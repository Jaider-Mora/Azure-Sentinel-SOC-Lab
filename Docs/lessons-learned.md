# Lessons Learned

## 1. Overview

This project provided practical experience building a defensive security monitoring laboratory using Microsoft Sentinel and a Linux endpoint.

The main objective was to understand how authentication telemetry can be collected, detected, enriched, and visualized as part of a SOC-oriented workflow.

The implemented workflow was:

```text
Linux Endpoint
      |
      v
rsyslog
      |
      v
Azure Monitor Agent
      |
      v
Data Collection Rule
      |
      v
Log Analytics Workspace
      |
      v
Microsoft Sentinel
      |
      v
KQL Detection
      |
      v
Attacker IP Extraction
      |
      v
GeoIP Enrichment
      |
      v
Workbook Visualization
```

## 2. Syslog Ingestion

One of the first important lessons was understanding that detection depends on the telemetry being correctly ingested into the Log Analytics Workspace.

The Linux endpoint generates authentication events through the SSH service. These events are handled by the system logging infrastructure and forwarded through the Azure Monitor Agent.

Before creating detections, it was necessary to verify that the expected Syslog events were actually reaching Microsoft Sentinel.

This establishes an important SOC principle:

Detection logic is only useful when the required telemetry is available and correctly normalized.

## 3. Azure Monitor Agent

Azure Monitor Agent acts as the collection component responsible for forwarding telemetry from the Linux endpoint to Azure.

The project demonstrated the importance of verifying that the agent is running correctly before troubleshooting Sentinel queries.

The validation process included checking the endpoint configuration and confirming that Syslog events were being ingested.

This helped separate collection problems from detection problems.

## 4. Data Collection Rule

The Data Collection Rule defines how telemetry from the Linux endpoint is collected and sent to the appropriate destination.

The project reinforced the importance of maintaining a clear relationship between:

 - Linux endpoint
 - Azure Monitor Agent
 - Data Collection Rule
 - Log Analytics Workspace
 - Microsoft Sentinel

If one component is incorrectly configured, the expected events may not reach the detection layer.

The DCR configuration was also exported and stored in the repository so that the laboratory configuration could be documented and reused.

## 5. Microsoft Sentinel and KQL

Microsoft Sentinel was used as the central SIEM platform for querying and investigating the collected telemetry.

Kusto Query Language was used to progressively transform raw Syslog events into useful security information.

The detection process was divided into multiple queries:

1. Failed SSH login detection.
2. Attacker IP extraction.
3. GeoIP enrichment.
4. Geographic attack visualization.

This separation made the investigation process easier to understand and document.

## 6. Failed SSH Authentication Detection

The baseline detection identifies events generated by sshd containing the Failed password message.

The detection uses a 30-day time window:

```kusto
| where TimeGenerated > ago(30d)
```

and filters events generated by the SSH daemon:

```kusto
| where ProcessName == "sshd"
```

The authentication failure condition is identified with:

```kusto
| where SyslogMessage has "Failed password"
```

This demonstrated how a relatively simple KQL query can transform raw authentication logs into a focused security investigation dataset.

## 7. Attacker IP Extraction

After identifying failed authentication attempts, the next step was extracting the source IP address from the Syslog message.

For example:

```text
Failed password for invalid user admin from 192.168.1.50 port 54321 ssh2
```

The query extracts:

```text
91.92.42.178
```

using a regular expression:

```kusto
extract(@"from\s+((?:\d{1,3}\.){3}\d{1,3})", 1, SyslogMessage)
```

This demonstrated how regular expressions can be combined with KQL to extract structured information from unstructured log messages.

## 8. GeoIP Enrichment

The extracted attacker IP addresses were enriched using the GeoIP_List Sentinel Watchlist.

The ipv4_lookup() operator was used to match the source IP against the network ranges contained in the watchlist:

```kusto
evaluate ipv4_lookup(_GetWatchlist("GeoIP_List"), AttackerIP, network)
```

The resulting geographic information included:

 - Country
 - City
 - Latitude
 - Longitude

Latitude and longitude were converted to numeric values before being used by the map:

```kusto
| extend Lat = todouble(latitude)
| extend Lon = todouble(longitude)
```

This demonstrated how external contextual data can be combined with security telemetry to improve investigation and visualization.

## 9. Workbook Visualization

The enriched dataset was used to create a geographic visualization in a Microsoft Sentinel Workbook.

The map uses:

| Map Setting         | Value                  |
| ------------------- | ---------------------- |
| Setting Information | Latitude and Longitude |
| Latitude            | `Lat`                  |
| Longitude           | `Lon`                  |
| Size                | `FailureCount`         |
| Size Aggregation    | `Sum`                  |
| Label               | `friendly_location`    |


The visualization provides a geographic representation of the observed failed SSH authentication activity.

The workbook configuration was exported to JSON and stored in:

```text
Sentinel/
└── WorkBooks/
    ├── README.md
    └── ssh-attack-map.json
```

This allows the visualization configuration to be version-controlled alongside the rest of the project.

## 10. Troubleshooting Lessons

The project also demonstrated the importance of troubleshooting each layer independently.

When an expected result is not visible in Sentinel, the problem should not immediately be assumed to be the KQL query.

The investigation should verify the complete data path:

```text
Linux
  |
  v
SSH / Syslog
  |
  v
Azure Monitor Agent
  |
  v
Data Collection Rule
  |
  v
Log Analytics
  |
  v
Sentinel
  |
  v
KQL
  |
  v
Workbook
```

This layered approach makes it easier to identify whether the problem is related to:

 - Event generation
 - Log collection
 - Data ingestion
 - Query logic
 - Watchlist enrichment
 - Visualization configuration

## 11. Security Considerations

The project demonstrated that security telemetry should be treated as contextual information rather than absolute evidence.

IP geolocation can provide useful investigative context, but it does not establish the physical identity or location of an attacker.

Factors such as:

 - VPNs
 - Proxies
 - NAT
 - Cloud infrastructure
 - Hosting providers
 - Geolocation database limitations

can affect the accuracy of the geographic information.

Therefore, the geographic information generated by this project should be considered enrichment for investigation rather than definitive attribution.

The main lesson from this project was understanding the complete path from raw security telemetry to actionable investigation context.

The laboratory implemented the following process:

```text
Telemetry
    |
    v
Detection
    |
    v

    v

    v
```

The project therefore demonstrates a practical SOC workflow using Linux authentication telemetry, Azure Monitor Agent, Microsoft Sentinel, KQL, Watchlists, GeoIP enrichment, and Workbooks.
